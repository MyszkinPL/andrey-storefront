# sealui — мастер-чеклист компонентов

## Протокол работы над каждым компонентом (обязателен)

1. **Читаем документацию Base UI целиком** — anatomy, все примеры, API reference
   каждой части (`https://base-ui.com/react/components/<name>`). Ничего не импровизируем.
2. **Смотрим исходники и реальные использования Polar** (если есть) — переносим визуальный язык и UX-паттерны; Polar — донор дизайна, не логики.
   Поведение и accessibility реализуем на Base UI, сверяя каждый режим с документацией его текущей версии. Если у Base UI есть дополнительные режимы, которых нет в Polar, оформляем их в существующем Polar-визуальном языке, не изобретая новую семантику.
3. **Реализуем** в `src/components/`: закрытый API (только enum-пропсы, без
   className/style снаружи), стили в `src/tokens.css` через `--seal-*` токены.
4. **Перепроверка по докам** — каждая использованная часть (`.Root`, `.Item`, …)
   и каждый проп существуют в API reference именно этой версии. Удаляем всё,
   чего нет в доках. Ловит также `tsc --noEmit`.
5. **Демо + сборка** — добавить на витрину, `npm run build` зелёный.
6. Ставить `[x]` в чек-листе только после визуальной проверки живого интерфейса; записать дату и результат в журнал проверок.

## Порядок реализации

Идём по сложности, а не по алфавиту: сначала простые визуальные элементы и композиции с небольшим объёмом состояния, затем интерактивные компоненты со сложным управлением, навигацией и валидацией.

Предварительная очередь:

1. Простые: Separator, Badge, Text/Heading, Avatar, Card/Setting, Stack/Cluster/Container, Banner, Well, DetailRow, StatisticCard, EmptyState.
2. Простые формы/составные: Button, Input/Textarea, Checkbox, Switch, Fieldset.
3. Средняя логика: Collapsible, Accordion, Tabs, Tooltip, Dialog, AlertDialog, CheckboxGroup, Field/Form.
4. Сложная логика: Select, Combobox, Popover, Menu/ContextMenu, RadioGroup, ToggleGroup, DateTimePicker, NumberField, OTPField и остальные навигационные/сложные компоненты.

Это рабочий порядок, не требование закрывать всю категорию за один раз. После каждого компонента сверяем UI с Polar и Base UI, затем двигаемся дальше.

## Принцип разделения источников

- **Polar** — визуальный источник: палитра, размеры, отступы, поверхности, композиции и UX-паттерны.
- **Base UI 1.8.0** — источник поведения, доступности и полного набора поддерживаемых режимов/частей.
- **Порядок: сначала Base UI-дока, затем Polar, потом расширения.** Читаем доку Base UI (anatomy, все props, состояния), затем переносим визуал Polar как первичный слой — его пресеты покрываем 1:1. Только после этого добавляем то, что есть в Base UI, но нет в Polar, оформляя это в том же визуальном языке без новой семантики.
- Возможности Base UI, отсутствующие у Polar, всё равно реализуются, но оформляются в визуальном языке Polar.
- Демо-компоненты добавляются в `src/catalog/stories/<component>.stories.tsx`; `import.meta.glob` автоматически включает их и объявленные варианты в каталог без изменения App/центральных импортов.
- Для нового компонента желательно покрывать все важные документированные состояния/режимы Base UI и показывать управляемые состояния, disabled/error/loading, где применимо.

### Правило работы для будущих волн (вывод из поломок 2026-10-08)

1. **Один писатель на файл.** Параллельные воркеры пишут только в свою именованную область, помеченную маркерами (`/* @seal:<id>:start */ … /* @seal:<id>:end */`). Маркеры выделяет координатор заранее, и они не пересекаются.
2. **Слои поверх базовых правил запрещены.** Если нужно поправить правило — правь сам источник, а не дописывай третий слой в конце файла. Именно так в тёмной теме появился почти-чёрный текст поля. Если правка требует чужого файла — пиши в отчёт, а не правь молча.
3. **Маркер вместо номера строки.** Строки в общем файле едут после каждой волны (tokens.css вырос с 3137 до 7600+ строк), поэтому ссылки «строка 1234» в отчётах устаревают мгновенно.
4. **Реэкспорт не создаёт локального имени.** `export { A as B }` не даёт использовать `B` внутри того же файла — либо локальная константа, либо прямое имя на месте.
5. **Не чинить то, что верно.** Перед «исправлением» числа/токена — цитата `файл:строка` из источника. В волне 5 три воркера независимо требовали «исправить» точные радиусы на неверные; спасли скептики.
6. **Воркеры не доверяют друг другу.** У каждого утверждения — доказательство; расхождения разводит координатор фактами, а не большинством голосов.
7. **Нет терминала — нет зелёного света.** Воркер не может сказать «сборка прошла»; проверки tsc/build делает координатор после сведения.
